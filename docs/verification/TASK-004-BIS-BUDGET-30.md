# BIS 누적 검증 한도 30회 승인 반영

최신 실제 소비: 2026-10-29 승인 후 4회 사용, 누적 **23/30회·잔여 7회**. [실측 기록](TASK-004-BIS-30-RUN-1.md)을 우선한다. 아래 19/30회·잔여 11회는 승인 직후의 과거 체크포인트다.

확인일: 2026-10-29 (Asia/Seoul). 사용자 지시: “BIS 사용량을 30으로 늘려”. 누적 검증 요청 상한을 기존 19회에서 30회로 늘리는 승인으로 반영했다. 제공기관 계정의 일/월 한도나 과금 설정 변경과 구분한다.

## 현재 사용과 승인

- 기존 실제 사용 체크포인트: 누적 19회.
- 신규 승인 상한: 누적 30회.
- 추가 사용 가능: 11회.
- 이번 실제 BIS 요청: 0회.
- 기존 실제 호출/실패/중단 기록과 NAVER 요청 이력은 변경하지 않았다.

src/data/bis-verification-budget.json에 승인 체크포인트/상한/일자를 보존했다. 이는 현재 확인된 사용량의 체크포인트이며 실시간 계정 사용량 API가 아니다. 후속 승인 범위 내 검증에서 실제 소비가 발생하면 장부 및 체크포인트 기록을 함께 갱신해야 한다. 동일한 추가 11회 예산을 다시 초기화하거나 승인 요청할 필요는 없다. 이번 지시는 즉시 11회를 전부 호출하라는 뜻으로 해석하지 않았다.

## 누락 장부 복구 및 안전장치

새 환경의 scratch에 이전 approved-16-19.sqlite는 없다. 이전 기록의 누적 19회 사용을 유지한 채 scripts/update-bis-budget.py로 /workspace/scratch/task004-research/bis-cumulative.sqlite를 복구했다. 사용량 0에서 시작하지 않았다. budget 행은 used=19, ceiling=30, halted=0이고 승인 감사행에는 이전 19/19에서 19/30으로의 갱신을 남겼다. 파일은 0600이며 저장소에 커밋하지 않는다. 위치/정류장 ID/키/응답/IP는 저장하지 않는다.

도구를 다시 실행해도 used를 감소시키지 않고, 이미 더 사용했으면 그 수치를 유지하며, 실패 중단 halted도 해제하지 않는다. 기존 상한을 낮추거나 사용량보다 낮게 설정하는 승인도 거부한다. SQLite BEGIN IMMEDIATE 예약 구조는 유지했다. 실제 API를 실행할 때만 JEJU_VERIFICATION_BUDGET_DB에 이 파일 경로를 지정한다. 이번에는 API 서버를 시작하거나 provider_rows를 호출하지 않았다. 새 환경에서는 자동으로 빈 파일을 생성해 재사용하지 말고 최신 실제 소비 기록을 먼저 확인해야 한다.

## Vercel과의 구분

Vercel에는 현재 외부 BIS를 호출하는 서버가 없다. 상한 승인만으로 조회 버튼을 활성화하지 않는다. 기존 “예산 소진” 안내는 “조회 서버 미연결”과 19/30회·잔여 11회 안내로 수정했다. 배포 요청 어댑터는 fetch 전에 서비스 미연결 상태 503을 반환하고, /api/* 정적 응답도 hosted_api_unavailable 및 체크포인트/상한을 표시한다. 이 정적 파일의 실제 HTTP 응답은 200이며 실제 BIS 서버/과금 차단 구현이라고 주장하지 않는다.

추가 11회는 현재 로컬 검증 장부로 제한된 승인 예산이다. 공개 Vercel 방문자의 요청으로 이를 직접 소비하게 만들지 않았다. 제공기관의 무료 조건/운영비/동시성 전체를 검증한 것은 아니다. 기존 두 저장소·기존 Vercel 프로젝트·메일 설정 변경 없음.
